# Headless layout harness

Track E1 — a regression gate that runs the V2 planner (Layers 1–5)
over a fixed synthetic terrain × forced-config battery outside of
Minecraft, in seconds, and diffs the per-run metrics against a
committed baseline. The point is to spot structural regressions
(like the HOUSE placement bug) in one prompt rather than ten.

## Running it

```
# Default — diff vs committed baseline, fail the test on regression.
./gradlew test --tests HeadlessHarnessTest

# Record a new baseline after a deliberate planner change.
./gradlew test --tests HeadlessHarnessTest -Dharness.mode=record
```

The committed baseline lives at `harness/baseline.json`. It captures
the system **as it is**, bugs included — a baseline that's "fixed"
things along the way is worthless as a regression gate. The first
recorded baseline must show the HOUSE bug visible in placement-rate
metrics.

The harness writes its output to standard out as a fixed-width table
designed for chat-paste:

```
TERRAIN        CONFIG       seed   plc/req rate    HOUSE%  cmpct   frUtil  comp  onMain  tViol   topDrop
FLAT           CITY/AGRI    1001   19/76   0.25    0.00    0.41    0.88    1     1.00    0.00    notsel:57
FLAT           TOWN/INDU    1002   ...
...
SUMMARY  mean placed-rate=...  mean HOUSE%=...  runs=36
DIFF vs baseline: PASS (no gated regressions)
```

When `check` fails, each failure prints with the run label, metric,
baseline, current, and signed delta.

## What the battery is

9 terrains × 4 forced (tier, inclination) configs = 36 runs. Seeds
are folded into the configs (one fixed seed each); the harness is
not a seed-sweep. The four configs are:

| Config              | What it exercises                                   |
| ------------------- | --------------------------------------------------- |
| `CITY/AGRICULTURAL` | HOUSE-bug reproducer — biggest composition, canary. |
| `TOWN/INDUSTRIAL`   | Resource path; cliff/forest anchors.                |
| `HAMLET/AGRICULTURAL` | Small-village floor; the case that mostly works. |
| `TOWN/CIVIC`        | Civic-core path; different topology than the others. |

If a config is nonsensical on a terrain (CITY on a small BASIN),
the run aborts naturally — the drop histogram captures it. The
harness does NOT filter combinations; an abort where work was
expected is exactly the signal we want.

The nine terrains are deterministic heightmaps generated by
[`SyntheticTerrainSource`](../src/main/java/tterrag1112/life_in_the_village/Village/Planning/V2/Layer1/SyntheticTerrainSource.java):
`FLAT`, `GENTLE_SLOPE`, `STEEP_SLOPE`, `VALLEY`, `RIDGE`, `CLIFF`,
`RIVER`, `BASIN`, `MIXED`.

## What the metrics mean

Per run the harness emits seven groups, computed entirely from data
the planner already produces (no new instrumentation inside Layers
1–5):

1. **Placement rate** — per-type and overall. Per-type
   `placedRate[HOUSE]` is the HOUSE-bug canary.
2. **Compactness** — `sum(footprint area) / area(bounding box of
   placed centres)`. Low = sprawled, high = dense.
3. **Frontage utilization** — two numbers:
   - `frac_buildings_on_network` — fraction with centre within
     `fp.length/2 + 6` of any edge centerline.
   - `road_coverage` — fraction of total centerline length with a
     building within setback.
4. **Connectivity** —
   - `network_components` — connected components of the edge graph
     (segments adjacent iff endpoints match). Healthy = 1.
   - `frac_buildings_on_main_component` — fraction whose nearest
     segment lives in the largest component.
5. **Terrain violence** — `(LEVEL + PLATFORM) / placed`. ~0 on FLAT;
   the key signal on slopes/cliffs for whether adaptation improves
   over time. `vegetation_per_placed` is recorded but always 0 in
   the harness (synthetic terrain has no trees).
6. **Clustering coherence** — per type with count ≥ 2,
   `mean(nearest-same-type distance) / mean(nearest-any distance)`.
   <1 = clusters, ≈1 = mixed, >1 = dispersed.
7. **Drop histogram** — counts by `DropReason`. Localizes where
   buildings are lost.

## Threshold policy — asymmetric, four metrics gate

`check` mode fails the test on these regressions (and only on the
bad direction):

| Metric                          | Threshold for failure |
| ------------------------------- | --------------------- |
| Per-type placement rate         | drop > 0.10 absolute  |
| Overall placed rate             | drop > 0.05 absolute  |
| `network_components`            | any increase          |
| `fracBuildingsOnMainComponent`  | drop > 0.05 absolute  |

Non-gating metrics — compactness, frontage utilization, road
coverage, terrain violence, clustering coherence, drop histogram —
print in every run but never fail the build. They will move
legitimately as the system evolves (clustering coherence is supposed
to drop below 1 when compound/nucleus work lands; terrain violence is
supposed to fall when adaptation improves). Gating them would make
every intentional change a fight with the harness.

Improvements never fail. A drop in placement rate is a regression;
an increase is signal you can record.

When a planner change is intended to move a gating metric: run
`check`, see the failure with the expected delta, eyeball that the
delta is the intended one, then re-record. The failure is a
confirmation prompt, not a stop sign.

## The no-planner-changes contract

The harness adds **only**:

- The `TerrainSource` and `FootprintProvider` seam interfaces.
- A `LiveTerrainSource` wrapping `ServerLevel` and the existing
  `StructureSizeCache` implementing `FootprintProvider` — both
  pure forwarding wrappers.
- A `SyntheticTerrainSource` and `FixedFootprintProvider` for the
  harness path.
- New overloads of `V2FeatureMap.scan`, `SiteAnalyzer.analyze`,
  `AnchorDetector.detect`, `PhasedPlanner.run`, and
  `TerrainAdapter.decide` that accept the seam types.
- A JUnit test in `src/test/java` plus the supporting
  battery / metrics / baseline / table code.

Layers 1–5 logic — composition, strategy selection, recipes,
placement, scoring, terrain adaptation — is unchanged. The live spawn
path is byte-identical: every existing call site keeps its existing
signature, and the `ServerLevel`-taking overloads delegate to the
new headless overloads through `LiveTerrainSource` wrappers (a 1:1
forwarder). `StructureSizeCache`'s warn-once / fallback-to-default
state lives where it always has.

If a future prompt requires the harness to "tweak" the planner to
make metrics look better, do not. The harness measures reality. Move
the threshold or re-record the baseline; do not edit the planner to
make the harness happy.

## Bootstrap caveat

`SyntheticTerrainSource` returns real `BlockState` instances
(`Blocks.WATER.defaultBlockState()` etc.) so `V2FeatureMap`'s
classifier — which exercises the real `BlockTags.LOGS`, `BlockTags
.LEAVES`, `Blocks.WATER` lookups — runs unmodified on the synthetic
path. That requires `Bootstrap.bootStrap()` to have populated the
static block / tag registries. The test calls it once in
`@BeforeAll`. It is the one Minecraft initialisation step the
harness needs; it does not load a world, generate chunks, or stand
up a server.

If the bootstrap call itself becomes slow or fragile, the alternative
is to move classification into `TerrainSource` (categorical reads
instead of `BlockState`). That trade was deliberately rejected —
moving classification means the synthetic source decides what's
water and what's forest, and you'd be testing the synthetic
classifier rather than V2FeatureMap's actual logic. Same principle
as "the baseline must show the HOUSE bug": the harness measures
the real code path or it measures nothing.

## Battery budget

Target: under 60 seconds total, including bootstrap. The 36-run
battery is pure compute over a 100-block-radius synthetic heightmap;
nothing in the planner does IO once `StructureSizeCache` is replaced
with `FixedFootprintProvider`.

If the budget creeps over 60s, that's a finding to report (planner
got slower, or a layer's complexity grew), not something to paper
over by shrinking the battery.
